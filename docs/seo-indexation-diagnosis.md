# SEO Indexation Diagnosis — cityee.ee

**Date:** 2026-07-06
**Author:** Technical SEO / Laravel engineering
**Method:** Static code review + live status-code testing against a local `php artisan serve` instance (127.0.0.1:8899), including Googlebot User-Agent parity checks. No production changes were made during diagnosis.

---

## 1. Executive summary

The site is a **single-domain, path-based multilingual Laravel app** (`cityee.ee`, `cityee.ee/ru/`, `cityee.ee/en/`). A large amount of SEO hardening already exists (redirect middleware, canonical/hreflang tags, sitemap generator, `X-Robots-Tag` control, audit config).

When the exact URLs reported by Google Search Console (GSC) are replayed against the current codebase, **the overwhelming majority already return `200` or a clean one-hop `301`.** This means most of the GSC report is **stale data** — errors that were fixed in earlier phases but not yet re-crawled/validated by Google.

The genuinely actionable problems are narrow and fall into four buckets:

| GSC group | Root cause | Where it lives | Action |
|---|---|---|---|
| Indexed though blocked by robots (`ru.cityee.ee/*`) | Legacy subdomain still resolving with its own robots.txt | **Server/DNS + app** | App-level host 301 + server rule |
| 403 Forbidden | **Not reproducible in Laravel** — every reported URL returns 200/301 locally, incl. with Googlebot UA | **Server / CDN / WAF** (Cloudflare or nginx) | Server rule (documented) |
| 5xx (≈47) | **Not reproducible** — no code path throws 500; bad slugs correctly return 404 | Transient (deploy window / timeout), already fixed | Monitor + defensive audit |
| 404 | Mostly stale (already 200). A few **genuinely changed/removed slugs** | App | Precise 301 map (this change) |

## 2. Architecture as-built (confirmed)

- **Routing:** `routes/web.php` — ET at root, RU under `/ru`, EN under `/en`. All content is path-based on one domain. There is **no** `ru.cityee.ee` route group in the app; the subdomain is a legacy artifact.
- **Middleware chain** (`bootstrap/app.php`): `RedirectOldUrls` → `CanonicalRedirects` (prepended, run first) → web → `NoIndexQueryParams` → `SeoHeaders`.
  - `RedirectOldUrls` — hardcoded old→new 301 map + query-string cleanup.
  - `CanonicalRedirects` — strips `/index`, `/index.html`, `/index.php`, collapses double slashes.
  - `NoIndexQueryParams` — sets `X-Robots-Tag: noindex, follow` when tracking/filter query params are present.
  - `SeoHeaders` — `Content-Language`, `Vary: Accept-Language`.
  - `TrailingSlash` — **exists but intentionally NOT registered** (would infinite-loop; canonical is handled by `<link rel=canonical>` instead).
- **robots.txt / sitemaps:** generated dynamically by `SitemapController` (routes in `web.php`), not static files.
- **Content sources:** DB (`Guide`, `AreaAudit` models, 15 published guides) + config files (`cityee-knowledge.php` pillar guides, `cityee-phase3.php` RU landings/districts/cases, `cityee-intent.php`).

### Critical finding: no Laravel layer returns 403
Reviewed all five middleware classes and all controllers. **None** issues `abort(403)`, applies `auth`/`can` gates to public content, or filters by User-Agent. Public pages have no authentication. Therefore any 403 Googlebot receives is produced **above Laravel** (CDN/WAF/web server).

## 4. Root-cause breakdown by GSC group

### 4.1 Indexed though blocked by robots.txt — `https://ru.cityee.ee/`, `https://ru.cityee.ee/kinnisvara-muuk`
- The canonical architecture is path-based (`cityee.ee/ru/…`). `ru.cityee.ee` is a **legacy subdomain**.
- Google has old `ru.cityee.ee` URLs in its index. They are "blocked by robots" because the subdomain host serves a restrictive `robots.txt` (its own vhost), so Google cannot fetch them to see a canonical/redirect — leaving them stuck as "indexed, blocked".
- **This is primarily a server/DNS concern** (the subdomain vhost). It is fixed by 301-redirecting the whole subdomain to the path-based equivalent. We add an **app-level host guard** as defence-in-depth (works if the subdomain reaches this app), and document the required server rule (the authoritative fix).

### 4.2 403 Forbidden — `/en/guides?category=…`, `/aleksandr-primakov`, `/knowledge/…`, `/guides/seo-strategi-2026`
- Reproduction: **impossible in Laravel.** Every listed URL returns 200 or a clean 301 locally, including under the Googlebot UA.
- The pattern — 403 concentrated on **query-string URLs** (`?category=`) and on **bot requests** — is the signature of a **WAF / CDN rule** (Cloudflare "Bot Fight Mode" / managed rules, or an nginx rule blocking query strings or non-browser UAs) returning 403 to Googlebot.
- **Fix is outside the repository** (§6 gives exact Cloudflare/nginx guidance). Nothing in Laravel needs to "fix" a 403 it never produced; doing so would mask the real layer.

### 4.3 Server error 5xx (≈47 URLs)
- Not reproducible against current code. Likely causes were **transient**: requests served during a deploy window (cache/opcache mid-swap), PHP memory/timeout, or a bug already resolved by earlier phases.
- Defensive posture: controllers already fail safe (404, not 500) on missing content. We add `seo:audit-sitemap` / `seo:audit-urls` so any real 5xx re-appearance is caught proactively before Google sees it.

### 4.4 404 Not Found
- Bulk of the list is **stale** (now 200 — see §3.2).
- Genuine cases are **changed or removed slugs**, fixed with precise one-hop 301s (§ fix report). We deliberately do **not** blanket-redirect to the homepage (avoids soft-404s).

## 5. What is Laravel vs. what is server/CDN

| Symptom | Layer | Fixed here? |
|---|---|---|
| Changed/removed slug → 404 | **Laravel** | ✅ 301 map |
| `/index`, `?category=`, query cleanup → 301 | **Laravel** | ✅ already working |
| `ru.cityee.ee` still indexed | **Server/DNS** (+ app guard) | ⚠️ app guard added; server rule required |
| 403 to Googlebot on public pages | **CDN / WAF / nginx** | ❌ documented only (not a code bug) |
| Transient 5xx | **Infra** (deploy/timeout) | ⚠️ audit tooling added to detect |

## 6. Server-level actions required (cannot be done in PHP)

These belong in nginx / Cloudflare and are the authoritative fixes for the subdomain + 403 groups:

```nginx
# 1. Legacy subdomain + www + http → canonical https path-based
server {
    listen 80;
    server_name cityee.ee www.cityee.ee ru.cityee.ee;
    return 301 https://cityee.ee$request_uri;
}
server {
    listen 443 ssl;
    server_name www.cityee.ee;
    return 301 https://cityee.ee$request_uri;
}
server {                                   # ru.cityee.ee/* → cityee.ee/ru/*
    listen 443 ssl;
    server_name ru.cityee.ee;
    return 301 https://cityee.ee/ru$request_uri;
}
```

**Cloudflare / WAF (403 group):**
- Ensure **Googlebot is not challenged/blocked**. In Bot Fight Mode / Super Bot Fight Mode, set *Verified Bots → Allow*.
- Remove/relax any managed or custom rule that returns 403 for requests containing a query string (`?category=`, `?type=`) — Google must be able to fetch them to see the 301.
- Verify with: `curl -A "Googlebot/2.1" -I "https://cityee.ee/guides?category=pricing"` from an external network. Expected: `301` (not `403`).

---

## 7. Verdict

- **Application code is largely healthy.** The site does not produce 403 or 5xx for public content, and returns correct 404 for invalid input.
- The remaining app-level work is a **small, precise 301 map** for changed/removed slugs plus a **subdomain host guard** — implemented in this change set.
- The **highest-impact remaining fixes are server-side** (subdomain redirect + WAF allow-Googlebot). Once those are in place, GSC validation for the robots and 403 groups can be started.
